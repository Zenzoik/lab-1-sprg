# Аналіз записів логічного аналізатора – ЛР2

Усі числа відтворюються командами `make decode` (декодування sigrok-cli 0.7.2 у `docs/captures/*.txt`) та `make measure` (`tools/measure.py` → `docs/captures/measurements.txt`). Графіки у `docs/lab_2/img/` будує `tools/plot_captures.py` з тих самих VCD.

## 0. Умови запису

| Параметр | Значення |
|---|---|
| Прилад | `wokwi-logic-analyzer` (Wokwi), експорт `wokwi.vcd`, timescale 1 нс |
| Запис 1 (основний) | `session_boot.vcd`: D0 SCL (PA9), D1 SDA (PA10), D2 SCK (PB3), D3 MOSI (PB5), D4 MISO (PB4), D5 CS# (PB0), D6 UART TX (PA2), D7 PWM1 (PA6); перші 1.5 с після скидання |
| Запис 2 (ADC) | `adc/session_adc.vcd`, схема `adc/diagram.json`: D0 маркер PB1, D1 SCL, D2 SDA, D3 UART TX, D4 PWM1 |
| Декодери sigrok | `i2c`, `spi` + `spiflash`, `uart` (115200 8N1), `pwm` |
| Нарізка | вікна по 0.5–50 мс із `session_boot.vcd` через `tools/vcd_tool.py window` (повний запис 96 с надто повільний для sigrok-cli) |

Прилад у симуляторі ідеальний: немає шуму, дзвону і фронтів кінцевої тривалості, а відліки часу – дискретні (кратні 25 нс у I2C-моделі). Тому вимірювання перевіряють логіку й часові співвідношення, але не електричні параметри.

## 1. I2C (MPU-6050, адреса 0x68)

### 1.1 Декодована послідовність WHO_AM_I (`i2c_whoami.txt`, рис. `i2c_whoami.png`)

```
Start  Address write: 68 ACK  Data write: 75 ACK  Stop
Start  Address read:  68 ACK  Data read:  68 NACK Stop
```

Порівняння з datasheet (Register Map RM-MPU-6000A, WHO_AM_I, 0x75): регістр існує, значення 0x68 – збігається. Адреса 0x68 відповідає AD0 = GND.

**Відхилення від рекомендованої послідовності.** Register Map описує читання регістра як START, AD+W, RA, повторний START, AD+R, дані, NACK, STOP. На шині видно STOP між фазами запису адреси регістра та читання, тобто повторного START немає. Причина – обхід Wokwi у `platform.c` (модель I2C не підтримує повторний START для HAL C0, див. журнал проблем). Реальний чіп приймає STOP + START, але для багатомастерної шини це ненадійно; на реальній платі увімкнути `BOARD_I2C_REPEATED_START=1`.

### 1.2 Ініціалізація (`i2c_init.txt`, `i2c_init.png`)

Після WHO_AM_I записуються, кожен окремою транзакцією: PWR_MGMT_1 (0x6B) ← 0x01 (вихід зі сну, джерело такту – PLL по X-гіроскопу), SMPLRT_DIV (0x19) ← 0x13 (1 кГц/20 = 50 Гц), CONFIG (0x1A) ← 0x03 (DLPF 44 Гц), GYRO_CONFIG (0x1B) ← 0x00 (±250 °/с), ACCEL_CONFIG (0x1C) ← 0x00 (±2 g). Усі байти ACK. Значення збігаються з таблицею регістрів.

### 1.3 Пакетне читання (`i2c_burst.txt`)

Запис регістра 0x3B, потім читання 14 байтів: `00 00 | 00 00 | 40 00 | EF 5C | 00 00 00 00 00 00`. Інтерпретація: ax = 0, ay = 0, az = 0x4000 = 16384 LSB = 1 g (чутливість ±2 g – 16384 LSB/g), температура 0xEF5C = −4260 → −4260/340 + 36.53 = 24.0 °C (формула з Register Map), гіроскоп 0. Останній прочитаний байт супроводжується NACK, як вимагає протокол.

### 1.4 Виміряні параметри (`measurements.txt`)

| Параметр | Виміряно | Розрахунок (TIMINGR 0x10805D88) | Висновок |
|---|---|---|---|
| Період SCL (медіана, 155 фронтів у вікні 48.5–50.4 мс) | 10.00 мкс (мін 10.00, макс 12.25) | 9.63 мкс + фронти | ≈ 100 кГц, збіг у межах 4 %; найбільший період 12.25 мкс – пауза на межі кадрів |
| Ширина високого рівня SCL | 5.00 мкс | tSCLH = 94 · 41.67 нс = 3.92 мкс | модель дає 50 % скважності; розрахунок менший, див. примітку |
| Транзакція запису регістра (START→STOP) | 197.25 мкс | 2 байти + адреса: 19.7 такту | збігається |
| Пакетне читання 14 байтів (START→STOP) | 1365.0 мкс | (9 + 14·9) = 135 тактів + START/STOP | збігається (136.5 такту) |

Примітка: у стандартному режимі (UM10204) tHIGH ≥ 4.0 мкс. Розрахунковий tSCLH = 3.92 мкс разом із синхронізацією фільтра дає межу; на реальному обладнанні варто збільшити SCLH на 2–3 одиниці (TIMINGR) або перевірити осцилографом.

### 1.5 Ручне декодування байта з осцилограми

Перша транзакція вікна: START при 392.40 мкс. SDA у моменти 9 наростаючих фронтів SCL: `1 1 0 1 0 0 0 0 | 0`. Перші вісім біти – `11010000` = 0xD0 = (0x68 << 1) | 0 (R/W = 0, запис), дев'ятий біт 0 – ACK від пристрою. Збігається з декодером sigrok (`Address write: 68`).

### 1.6 Аномалія: адреса 0x69 (`i2c_anomaly_nack.txt`, `i2c_nack.png`)

```
Start  Address write: 69  NACK  Stop
```

Прошивка навмисно опитує 0x69 (AD0 = VCC). Датчик підключений з AD0 = GND, тому відповіді немає – NACK на дев'ятому такті, SDA залишається високою. Це підтверджує, що драйвер відрізняє «пристрою немає» від «шина зависла» (результат `NACK`, не `TIMEOUT`), а також перевіряє, що адреса 0x68 справді відповідає за AD0 = GND.

## 2. SPI (W25Q64)

### 2.1 JEDEC ID (`spi_jedec.txt`, `spi_jedec.png`, `spi_byte.png`)

```
Command: Read identification (RDID)
Manufacturer ID: 0xef  Memory type: 0x40  Device ID: 0x17
```

Збігається з datasheet W25Q64JV (EF 40 17). Перший байт: MOSI = 0x9F (біти 1001 1111 у моменти наростаючого фронту SCK, див. `spi_byte.png`); три наступні клоки приймають EF, 40, 17. Під час передачі команди MISO не має значення (у моделі читається 0x7F). Декодер sigrok підписує виробника як «Adesto Unknown» – у таблиці виробників цієї версії sigrok код 0xEF не зіставлений з Winbond; на коректність декодування бітів це не впливає.

Параметри кадру:

| Параметр | Виміряно | Очікування |
|---|---|---|
| SCK | 3.08 МГц (період 0.33 мкс; 32 фронти = 4 байти) | 48 МГц / 16 = 3 МГц |
| CS# низький | 240.75 мкс | 4 байти · 8 · 0.333 = 10.7 мкс (без пауз) |
| CS↓ → перший фронт SCK | 24.98 мкс | накладні витрати HAL і програмного CS |
| Паузи між байтами | 99.4 мкс після команди, далі 17.1 + 17.1 мкс | – |

Режим: CPOL = 0, CPHA = 0 (mode 0) – дані стабільні на наростаючому фронті, як вимагає W25Q64JV (підтримує mode 0 і 3). CS тримається низьким усю команду (cmd + відповідь) – вимога datasheet; кадр завершується піднятим CS.

Часові параметри значно гірші за розрахунок: ефективна швидкість 4 байти / 240 мкс ≈ 133 кбіт/с замість 3 Мбіт/с. Причина – HAL_SPI_Transmit/Receive викликаються окремими функціями з накладними витратами. Для сторінкового читання це вузьке місце; для керування – допустимо (одна транзакція << 20 мс періоду циклу керування).

### 2.2 Стирання, write-enable, програмування (`spi_erase.txt`, `spi_program_read.txt`)

Послідовність у записі:

```
WREN → RDSR (WEL = 1) → Sector erase (SE) 0x001000 → RDSR … RDSR (WIP = 1, потім 0)
WREN → RDSR (WEL = 1) → Page program (PP) 0x0010F8, 8 байтів a0..a7 → RDSR (WIP = 1) … (WIP = 0)
Read (0x03) 0x0010F8 → дані
```

Вимога datasheet «write-enable перед кожним записом/стиранням» виконана: перед SE і PP є окремі транзакції WREN (CS піднімається між ними), статус після WREN показує WEL = 1, після команди – WEL = 0, WIP = 1. Час стирання сектора: від кінця команди SE (CS↑ при 67.5 мс) до останнього опитування RDSR з WIP = 0 (112.96 мс) ≈ 45.4 мс, що збігається з типовим tSE = 45 мс (максимум 400 мс) у datasheet. Опитування RDSR виконується приблизно кожні 213 мкс.

Адреса 0x0010F8 + 16 байтів перетинає межу сторінки 0x1100; драйвер розбиває запис на дві PP-команди (перевіряється також host-тестом).

### 2.3 Аномалія: SPI mode 3 (`spi_anomaly_mode3.txt`, `spi_anomaly_mode3_cpol1.txt`)

Прошивка свідомо перемикає SPI в CPOL = 1, CPHA = 1 і надсилає 0x9F. Декодер spiflash (mode 0 за замовчуванням) бачить `Unknown command: 0xcf`, потім 0xff… Той самий запис, декодований як `spi:cpol=1:cpha=1`, дає коректні байти. Висновок: при розходженні режиму декодера й шини дані зсуваються на біт: 0x9F (1001 1111) читається як 0xCF (1100 1111), бо перший фронт SCK приходиться на неправильну фазу. Це типова ознака неправильних CPOL/CPHA, яку видно саме на логічному аналізаторі.

## 3. UART (USART2, PA2)

`uart_banner.txt` (sigrok, 115200 8N1, ASCII): `hello from STM32 (lr2)`, `SELFTEST BEGIN version=lr2 t_ms=4`, `DEV mpu6050_id status=OK addr=0x68 who=0x68 expected=0x68` та подальші рядки самоперевірки.

| Параметр | Виміряно | Розрахунок |
|---|---|---|
| Тривалість біта (найкоротший низький імпульс) | 8.68 мкс (115274 бод) | 1/115200 = 8.68 мкс; фактично 48 МГц/417 = 115108 бод |
| Формат кадру | start (0), 8 біт LSB першим, stop (1) | 8N1 |

Ручне декодування (рис. `uart_bits.png`): символ 'h' = 0x68 = 0110 1000; на осцилограмі після start-біта (низький) йдуть біти LSB першим 0, 0, 0, 1, 0, 1, 1, 0 і stop-біт високий. Збігається з декодером. Рядки самоперевірки мають формат `DEV <name> status=OK|FAIL <key=value ...>` – їх розбирає скрипт без регулярних виразів на вільний текст.

## 4. PWM (TIM3 CH1, PA6)

Демо-послідовність прошивки: 1000, 2000, 1500 мкс по 100 мс кожна, період 20 мс.

| Імпульс (задано) | Виміряно (округлено до 10 мкс) | Кількість імпульсів у записі | Duty (sigrok) |
|---|---|---|---|
| 1000 мкс | 1000 | 6 | 5.0 % |
| 2000 мкс | 2000 | 5 | 10.0 % |
| 1500 мкс | 1500 | 7 | 7.5 % |

Період (медіана) 20000 мкс = 50 Гц, збігається з ARR = 19999 при тіку 1 мкс. Діапазон 1–2 мс відповідає специфікації сервоприводу SG92R (положення 0°…180° при 1–2 мс, період 20 мс). Рис. `pwm_widths.png`.

## 5. ADC і службовий маркер (запис 2)

| Параметр | Виміряно |
|---|---|
| Імпульсів маркера PB1 | 51 |
| Тривалість імпульсу (ширина вікна вимірювання ADC + читання) | 63.60 мкс (мін = макс) |
| Період маркера | 19995.58 мкс = 50.01 Гц (цикл керування) |
| Затримка: спад маркера → START наступної I2C-транзакції | 37.02 мкс (мін = макс, n = 50) |

Затримка «подія прошивки → зміна на шині» розкладається так: маркер піднімається перед `HAL_ADC_Start`, падає після `HAL_ADC_GetValue`; за наступні 37 мкс драйвер готує пакетне читання MPU-6050 і виставляє START. Результат АЦП у цьому запису – raw = 300 (≈ 242 мВ): атрибут `value` потенціометра в `adc/diagram.json` дорівнює 75 зі шкали 0–1023, тобто 75/1023 · 3.3 В = 0.242 В, що збігається з вимірюванням. В основному записі `diagram.json` потенціометр лишився зі значенням за замовчуванням 0, тому там `adc raw=0` – це правильний результат для 0 В, а не помилка. Розрахункова тривалість самого перетворення – 0.58 мкс (14 тактів при 24 МГц), тому 63.6 мкс складаються переважно з накладних витрат HAL (запуск, опитування EOC, читання). Рис. `adc_marker.png`.

## 7. Знайдені аномалії (підсумок)

1. NACK на 0x69 – очікувана, підтверджує адресацію (розд. 1.6).
2. Немає повторного START при читанні регістра – обхід симулятора (розд. 1.1), на реальному обладнанні ввімкнути `BOARD_I2C_REPEATED_START`.
3. SPI mode 3 дає «неіснуючу» команду 0xCF – помилка режиму видна одразу (розд. 2.3).
4. CS-low 240 мкс замість 10.7 мкс і паузи 99 мкс між командою та відповіддю – накладні витрати двох викликів HAL (розд. 2.1).
5. sigrok підписує EF як «Adesto» – обмеження таблиці виробників декодера, не помилка шини.
